# 随手记功能设计方案

## 1. 目标

为 Creta 增加一个“随手记”能力，让用户在打开主输入框后，通过固定关键词快速进入记笔记模式，立即记录临时想法、待办事项和灵感内容。

这个功能的核心价值是：

- 进入快：不需要先打开独立笔记软件
- 记录轻：一句话即可保存
- 检索快：新建记录的同时也能搜到旧内容
- 心智清晰：显式进入“随手记模式”，不干扰普通搜索

## 2. 设计结论

推荐将“随手记”实现为一个独立的内置插件模式，而不是直接修改主输入框的全局搜索行为。

推荐入口方案：

- Action Keyword 使用 `n`
- 同时提供一个专属快捷键，用于唤起 Creta 并自动预填 `n `

这样可以同时兼顾：

- 高频使用时的输入效率
- 与现有 Creta 查询架构的兼容性
- 对普通全局搜索体验的最小影响

## 3. 为什么推荐 `n`

在当前架构下，查询是按“首个词是否精确匹配 Action Keyword”来分发的，而不是按前缀匹配。

因此：

- 输入 `n` 会进入随手记模式
- 输入 `n 今天整理方案` 会进入随手记模式
- 输入 `notion`、`node`、`new`、`npm` 不会进入随手记模式

这意味着 `n` 不会和“以 n 开头的普通搜索”发生冲突，只会在“首个完整词就是 n”时才触发。

## 4. 典型使用场景

### 场景 1：快速记录灵感

用户打开 Creta，输入：

```text
n 给插件系统增加轻量笔记能力
```

结果列表第一项显示：

- 保存这条笔记

用户回车后立即保存。

### 场景 2：边记边搜

用户输入：

```text
n chrome 标签搜索
```

结果列表同时显示：

- 保存“chrome 标签搜索”
- 已有笔记：Chrome 标签页搜索说明
- 已有笔记：tab 插件设计草案

用户可以决定新建，或者直接打开已有记录。

### 场景 3：查看最近记录

用户输入：

```text
n
```

结果列表显示：

- 最近笔记
- 置顶笔记
- 今天的记录
- 常用操作

### 场景 4：集中整理笔记

用户打开 Creta 设置，进入 Quick Note 插件的「笔记管理」页；或在 `n` 主页选择「打开笔记管理器」。

界面以表格形式展示全部（或筛选后的）笔记，用户可以：

- 搜索、按标签或状态筛选
- 修改标签、置顶或归档
- 编辑正文、删除过期记录
- 一次处理多条笔记

适用场景：笔记积累到一定数量后，需要批量整理、改标签、清理归档，而不是在启动器结果列表里逐条右键操作。

## 5. 推荐交互设计

### 5.1 进入方式

- 输入 `n`
- 输入 `n 空格 + 内容`
- 使用专属快捷键直接打开并预填 `n `

推荐把“快捷键预填 `n `”作为高频入口，因为这会明显降低使用门槛。

### 5.2 结果列表行为

当输入为 `n` 时：

- 展示最近笔记
- 展示置顶笔记
- 展示“查看今天记录”“查看最近 20 条”等快捷操作

当输入为 `n 内容` 时：

- 第一条结果固定为“保存这条笔记”
- 下方展示与该内容相关的已有笔记
- 支持直接回车保存

### 5.3 保存后的行为

保存成功后关闭主窗口，保持简单直接。

### 5.4 笔记集中管理界面

启动器结果列表适合「快记、快搜、单条操作」，不适合一览全局和批量整理。因此推荐增加独立的**笔记集中管理界面**，与启动器入口职责分离：

| 场景 | 推荐入口 |
| --- | --- |
| 快速记一句话 | `n 内容` → 回车 |
| 搜索已有笔记 | `n 关键词` / `#标签` |
| 编辑长文 | 结果项 → 编辑器窗口 |
| 批量整理、改标签、删过期笔记 | 笔记管理界面 |

**主入口：** Creta 设置 → 插件 → Quick Note →「笔记管理」Tab（与现有「存储设置」Tab 并列）。

**辅助入口（可选）：** 在 `n` 主页增加「打开笔记管理器」快捷项，跳转到设置页的管理 Tab 或直接打开管理窗口。

**展示形式：** 采用与 Program、WebSearch 等插件一致的 `ListView + GridView` 表格，而非把表格塞进启动器结果列表。

建议列：

- 内容摘要（单行截断，双击打开多行编辑器）
- 标签（展示 `#tag`，支持独立编辑）
- 创建时间 / 更新时间（可排序）
- 置顶 / 归档（图标或 Checkbox，可快速切换）
- 操作（编辑、删除；或通过工具栏 + 多选统一处理）

顶部工具栏：

- 搜索框：过滤内容与标签
- 筛选：全部 / 置顶 / 归档 / 按标签
- 批量操作：删除选中、批量归档、批量改标签
- 刷新：重新加载 `notes.json`（应对外部文件修改）

详细设计见 [第 14 节](#14-笔记集中管理界面设计)。

## 6. 数据模型建议

第一版建议采用最小可用模型：

- `Id`
- `Content`
- `CreatedAt`
- `UpdatedAt`
- `IsPinned`

第二阶段可扩展：

- `Tags`
- `Archived`
- `LastViewedAt`
- `Source`

## 7. 存储方案建议

第一版推荐使用本地 JSON 存储。

原因：

- 实现简单
- 易于调试
- 适合 MVP
- 数据量在早期通常不会大到需要数据库

当后续需求扩大，例如：

- 记录数量明显增长
- 需要更复杂的搜索
- 需要排序、过滤、统计能力

再切换为 SQLite 会更合适。

## 8. MVP 功能范围

第一版推荐只做以下能力：

- 支持通过 `n` 进入随手记模式
- 支持输入内容后直接保存
- 支持展示最近笔记
- 支持按关键词搜索已有笔记
- 支持复制笔记内容
- 支持编辑笔记
- 支持删除笔记
- 支持置顶笔记

这版已经足够支撑“平时记笔记”和“快速记录灵感”的核心用途。

## 9. 后续增强方向

在 MVP 验证通过后，可以逐步增加：

- 多行编辑窗口
- 标签系统
- 按日期分组
- 今天记录 / 本周记录视图
- **笔记集中管理界面**（表格展示、删除、改标签、批量整理）
- Markdown 导出
- 文本导入
- 固定模板插入
- AI 总结最近笔记
- **单向同步到 Notion Database**（新建笔记追加为 Database 页面）

## 10. 不推荐的方案

不推荐把随手记设计成“普通输入自动识别是否应该记笔记”。

原因：

- 会干扰主搜索框的通用搜索行为
- 用户不容易理解当前是在搜索还是在记录
- 会提升误触概率
- 与 Creta 现有的关键词路由机制不一致

显式关键词模式更符合 Creta 的产品心智，也更容易维护。

也不推荐把笔记管理表格直接做进启动器结果列表。

原因：

- 结果列表有数量上限（如最近 8 条、浏览 20 条），无法承载全量笔记一览
- 表格列、多选、批量操作在窄结果列表中交互体验差
- 与 Creta「键盘快搜」的产品心智不一致

集中管理应放在插件设置页或独立管理窗口，启动器继续负责快记快搜。

## 11. 最终推荐

推荐采用以下方案作为第一版：

- 将随手记实现为独立内置插件
- Action Keyword 使用 `n`
- 提供专属快捷键并预填 `n `
- `n` 显示最近记录与快捷操作
- `n 内容` 默认提供“保存这条笔记”
- 同时显示匹配的历史笔记
- 本地使用 JSON 保存数据
- 结构化阶段增加插件设置页「笔记管理」表格界面，承担删除、改标签、批量整理

这个方案在输入效率、实现复杂度、可扩展性和对现有架构的兼容性之间，整体最均衡。

## 12. 逐阶段实现方案

为了降低一次性实现的复杂度，建议将“随手记”拆成多个阶段推进。每一阶段都应形成可以独立验证和交付的结果。

### 阶段 1：最小可用版本

目标：

- 先让用户能够稳定进入随手记模式
- 先完成“快速记录”这一核心价值

实现范围：

- 新增独立内置插件
- 配置 Action Keyword 为 `n`
- 支持输入 `n 内容` 后直接保存笔记
- 支持输入 `n` 时显示最近笔记
- 使用本地 JSON 文件保存数据
- 每条记录保存 `Id`、`Content`、`CreatedAt`、`UpdatedAt`、`IsPinned`

这一阶段不做：

- 多行编辑窗口
- 标签系统
- 复杂筛选
- 导入导出

完成标志：

- 用户可以通过 `n` 进入模式
- 用户可以回车保存一条新笔记
- 重新打开后可以看到最近记录

### 阶段 2：新建与检索并行

目标：

- 提升“记过的内容能立刻找回”的使用价值
- 避免重复记录

实现范围：

- 当输入 `n 内容` 时，第一条结果固定显示“保存这条笔记”
- 同时根据输入内容搜索历史笔记
- 历史笔记结果支持打开查看和复制内容
- 对最近记录和命中记录进行基础排序

这一阶段的重点：

- 一次输入同时支持“新建”和“查旧”
- 让“边记边搜”的产品心智真正成立

完成标志：

- 用户输入新内容时，既能保存，也能立刻看到相关旧笔记
- 历史记录搜索结果具有基本可用性

### 阶段 3：基础管理能力

目标：

- 让随手记从“能记”升级到“能管理”

实现范围：

- 支持编辑笔记
- 支持删除笔记
- 支持置顶笔记
- 支持复制笔记内容
- 支持查看今天记录和最近若干条记录

这一阶段的重点：

- 补齐日常维护笔记所需的核心操作
- 提高用户长期使用意愿

完成标志：

- 用户不需要离开 Creta，也能完成常用的笔记整理动作

### 阶段 4：增强录入体验

目标：

- 适配更长内容和更复杂的记录场景

实现范围：

- 增加多行编辑窗口
- 支持从结果中进入编辑态

这一阶段的重点：

- 解决单行输入框不适合长内容编辑的问题

完成标志：

- 用户既可以快速记一句话，也可以顺畅记录较长内容

### 阶段 5：结构化与归档能力

目标：

- 让笔记从“临时记录”逐步演进为“可整理的信息池”

实现范围：

- 支持标签
- 支持归档
- 支持按日期分组
- 支持“今天”“本周”“置顶”视图
- 支持简单筛选与排序
- **新增笔记集中管理界面**（见 [第 14 节](#14-笔记集中管理界面设计)）

管理界面 MVP 范围：

- 在插件设置页增加「笔记管理」Tab，表格展示全部笔记
- 单条：编辑内容、删除、置顶/归档切换、独立修改标签
- 按关键词 / 标签 / 状态筛选
- 复用现有 `NoteEditorWindow` 与 `NoteRepository`

管理界面第二版范围：

- 多选 + 批量删除 / 批量归档 / 批量加标签
- 列排序、导出选中项（txt/md）
- 从管理页打开 `notes.json` 所在文件夹

这一阶段的重点：

- 提升信息组织能力
- 让记录不只是堆积，而是可以被重新利用
- 补全启动器「单条操作」在批量整理上的不足

完成标志：

- 用户可以按主题、时间或状态管理自己的随手记内容
- 用户可以在设置页的表格中完成删除、改标签等集中维护，而不必逐条使用右键菜单

### 阶段 6：导入导出与扩展能力

目标：

- 提升数据可迁移性和生态扩展能力

实现范围：

- 支持导出为 `txt` 或 `md`
- 支持导入已有文本内容
- 评估是否从 JSON 升级到 SQLite
- 为后续 AI 总结、模板插入等能力预留数据结构

这一阶段的重点：

- 降低数据锁定风险
- 为后续高级能力铺路

完成标志：

- 用户的记录可以方便备份、迁移和再利用

## 13. 推荐实施顺序

如果希望尽快上线并验证价值，推荐按下面顺序推进：

1. 阶段 1：最小可用版本
2. 阶段 2：新建与检索并行
3. 阶段 3：基础管理能力
4. 阶段 4：增强录入体验
5. 阶段 5：结构化与归档能力
6. 阶段 6：导入导出与扩展能力

其中，阶段 1 到阶段 3 已经足够构成一个可长期使用的第一版产品。后续阶段主要用于提升体验和扩展性。

阶段 5 中的「笔记集中管理界面」可在标签、归档等结构化能力就绪后推进，是随手记从「能记能搜」到「能整理能维护」的关键一步。

## 14. 笔记集中管理界面设计

### 14.1 设计动机

当前随手记已通过启动器完成快速记录、搜索和单条维护（右键菜单：编辑、删除、置顶、归档等）。但随着笔记数量增长，以下痛点会显现：

- 启动器结果列表有数量上限，难以一览全部笔记
- 删除、改标签等操作分散在每条笔记的右键菜单中，批量整理效率低
- 标签目前主要从正文 `#tag` 解析，缺少「只改标签、不动正文」的独立编辑能力

因此需要增加**集中管理界面**：启动器继续负责「快记快搜」，管理界面负责「一览全局、批量整理」。

### 14.2 入口与布局

**主入口：**

```
Creta 设置 → 插件 → Quick Note
├── Tab 1：存储设置（现有 SettingsControl）
└── Tab 2：笔记管理（新增 NotesManagerControl）
```

**辅助入口（可选）：**

- 在 `n` 主页增加「打开笔记管理器」结果项，跳转到设置页的管理 Tab 或弹出独立窗口

**UI 技术选型：**

- 与 Program、WebSearch、Sys 等插件保持一致，使用 `ListView + GridView`
- 不采用将表格嵌入启动器结果列表的方案

### 14.3 表格设计

| 列 | 说明 |
| --- | --- |
| 内容摘要 | 单行截断；双击打开 `NoteEditorWindow` |
| 标签 | 显示 `#tag1 #tag2`；支持行内编辑或弹窗编辑 |
| 创建时间 / 更新时间 | 支持列头点击排序 |
| 置顶 / 归档 | 图标或 Checkbox，可快速切换 |
| 操作 | 编辑、删除（或通过工具栏 + 多选统一处理） |

**顶部工具栏：**

- 搜索框：过滤内容、标签
- 筛选：全部 / 置顶 / 归档 / 按标签
- 批量操作：删除选中、批量归档、批量改标签
- 刷新：重新加载 `notes.json`

### 14.4 功能分阶段

**MVP：**

- 表格展示全部笔记（数据量大时使用分页或虚拟化，如每页 50 条）
- 单条：编辑内容、删除、置顶/归档切换
- 独立修改标签（不强制修改正文）
- 按关键词 / 标签筛选

**第二版：**

- 多选 + 批量删除 / 批量归档 / 批量加标签
- 列排序、导出选中项（txt/md）
- 「在文件夹中打开 notes.json」

### 14.5 数据层扩展

现有 `NoteRepository` 已支持增删改、置顶、归档、按标签筛选，管理界面建议小幅扩展：

```csharp
// 建议新增
bool SetTags(string noteId, IReadOnlyList<string> tags, ...);
IReadOnlyList<NoteItem> GetAllNotes();  // 管理页用，不受启动器 20 条浏览上限约束
void Reload();                          // 管理页打开或点击刷新时重新读取文件
```

**标签编辑策略：**

- **独立字段优先**：以 `Tags` 数组为准，展示时拼接为 `#tag`
- 保存正文时仍可从内容解析 `#tag` 并合并，保持现有输入习惯
- 管理页改标签时调用 `SetTags`，用户不必在正文中查找 `#`

### 14.6 架构关系

```text
SettingsControl (TabControl)
├── StorageSettings（现有）
└── NotesManagerControl（新增）
        ├── NotesManagerViewModel
        ├── NoteRepository（复用）
        └── NoteEditorWindow（复用）

启动器 n 主页 ──可选──→ NotesManagerControl
```

- `NotesManagerViewModel`：维护 `ObservableCollection`，封装筛选、选中、命令
- `Main.CreateSettingPanel()`：返回带 Tab 的容器，注入 `NoteRepository` 引用
- 管理页保存后，仓储为插件内单例，启动器下次 Query 自然读到最新数据

### 14.7 边界与注意事项

- **性能：** 笔记量大时表格需分页或虚拟化；搜索可走内存过滤，暂不必升级 SQLite
- **安全：** 批量删除需二次确认，避免误操作
- **同步：** 若用户在外部编辑 `notes.json`，管理页提供「刷新」按钮；删除/改标签后即时写回文件
- **职责分离：** 不在启动器结果列表中实现表格；启动器与管理界面各司其职

## 15. 单向同步到 Notion

目标：`n xxx` 仍以本地 `notes.json` 为主存储；打开同步后，新建笔记在本地保存成功后再追加到用户指定的 Notion Database。

### 15.1 范围

- 同步：启动器 `n 内容` 新建、编辑器新建且带正文
- 不同步：编辑、删除、归档、导入、历史存量、截图附件上传
- 纯图笔记（无正文）跳过 Notion

失败不影响本地记录；设置页可测试 Integration Token 与 Database 连接。

### 15.2 配置

Creta 设置 → 插件 → Quick Note → Notion：

1. 在 [notion.so/my-integrations](https://www.notion.so/my-integrations) 创建 Internal Integration 并复制 Token
2. 打开目标 Database，通过 Connections 把该 Integration 加进去
3. 填写 Database 链接或 32 位 ID，并打开「保存新笔记时同步到 Notion」

运行时读取 Database schema：自动使用 `title` 列；若存在名为 `Tags` / `标签` / `tags` 的 `multi_select` 列则写入标签。正文写入页面 paragraph 子块。
